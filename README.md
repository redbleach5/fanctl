# FanBar — ручное управление вентиляторами и мониторинг MacBook (Apple Silicon)

Инструмент для MacBook Pro с Apple Silicon: **плавное ручное управление
вентиляторами** и **живой мониторинг** температур/нагрузки — для случая, когда
машина долго работает на локальном инференсе моделей и нужно гарантировать
достаточное охлаждение.

Проверено на **MacBookPro18,4 (M1 Max), macOS 26.4**.

## Состав

| Компонент | Что делает | Права |
|---|---|---|
| **FanBar.app** | Иконка в менюбаре: температуры, обороты, ползунок, память/процессы, график за 10 минут | пользователь (чтение) |
| **fanctld** | Демон: плавный разгон/торможение, аварийная защита, сокет управления | **root** (LaunchDaemon или `sudo`) |
| **fanctl** | CLI: status / watch / temps / processes / set / auto / start / quit | пользователь (запись — через демон) |

Мониторинг работает **без** демона (SMC и HID-датчики читаются без root).
Управление вентиляторами возможно только при запущенном `fanctld`.

## Установка

```bash
./scripts/install.sh
```

Собирает release, создаёт `/Applications/FanBar.app` (ad-hoc подпись),
копирует `fanctl`/`fanctld` в `/usr/local/bin` и устанавливает LaunchDaemon
`local.fanbar.fanctld`. Демон запускается при загрузке и автоматически
перезапускается после аварийного завершения. Перед установкой старая версия
демона на `/tmp/fanctl.sock` останавливается с возвратом вентиляторов в auto.
После установки FanBar автоматически перезапускается, чтобы уже открытая
старая версия не продолжала использовать прежний сокет.

Запуск приложения:

```bash
open /Applications/FanBar.app
```

Автозапуск при входе (по желанию):

```bash
osascript -e 'tell application "System Events" to make login item at path "/Applications/FanBar.app"'
```

## Использование

### Менюбар (FanBar)

- **Температура в строке меню** — максимальная температура (⚠ при аварии).
- **Температуры**: CPU (датчики `Tp*`), GPU (`Tg*`), SSD (NAND), батарея, максимум.
- **Вентиляторы**: текущие обороты, ползунок цели, пресеты «Тихо / Баланс / Максимум»,
  кнопка **Auto** (вернуть управление SMC).
- **Нагрузка**: CPU %, GPU %, RAM/swap, доступная память и топ процессов по physical footprint.
- **График**: температура и обороты за последние 10 минут по фактическому времени замеров.
- Кнопка **Запустить** поднимает `fanctld` (диалог пароля администратора),
  **Стоп** — корректно останавливает (вентиляторы уходят в auto).

### CLI

```bash
fanctl status        # снимок: режим, вентиляторы, температуры, нагрузка
fanctl watch         # то же, обновление каждую секунду
fanctl temps         # все SMC/HID-датчики, по убыванию температуры
fanctl processes     # детали RAM и топ-16 процессов по physical footprint
fanctl set 3000      # ручной режим: цель 3000 RPM (нужен запущенный fanctld)
fanctl auto          # вернуть управление SMC
fanctl start         # запустить fanctld (пароль администратора)
fanctl quit          # остановить fanctld (всегда возвращает auto)
fanctl read F0Ac     # прочитать сырой ключ SMC
```

Запуск демона вручную из терминала:

```bash
sudo fanctld                      # defaults: warn 85°C, critical 95°C
sudo fanctld --warn 80 --critical 92 --log /tmp/fans.csv --interval 500
sudo fanctld --help
```

## Как это работает

### Запись в вентиляторы (SMC)

AppleSMC открывается через IOKit (`selector 2`), ключи читаются командами
`data8 = 9` (key info) / `5` (чтение), запись — `data8 = 6` с явным размером
полезной нагрузки. Ключи вентиляторов:

- `F{n}Md` — режим: `1` принудительный, `0` auto;
- `F{n}Tg` — целевые обороты (тип `flt `, 4 байта);
- `F{n}Ac` — фактические обороты, `F{n}Mn` / `F{n}Mx` — минимум/максимум.

**Порядок записи критичен:** сначала `F{n}Md = 1`, затем `F{n}Tg = <rpm>` —
запись цели в auto-режиме молча игнорируется. Проверено эмпирически
(`probe/smc_wtest2.c`): цель применяется за ~1 c, разгон идёт физически
плавно (~1000 RPM/с), возврат в auto сбрасывает цель и вентиляторы останавливаются.

### Датчики

- **SMC** (~219 ключей `T*`, тип `flt `): `Tp*` — CPU, `Tg*` — GPU,
  `TC*` — SoC, максимум SMC используется для аварийной защиты.
- **HID** (без root, именованные): `NAND CH0 temp` — SSD,
  `gas gauge battery` — батарея, `PMU tdie*` и другие PMU. Все HID-датчики
  выводятся в `fanctl temps` и участвуют в отображаемом общем максимуме.
- **Система**: CPU % (`host_processor_info`), GPU % (`AGXAccelerator` →
  `Device Utilization %`), RAM/swap (`host_statistics64`, `vm.swapusage`),
  доступная память (`kern.memorystatus_level`).
- **RAM**: основное значение — `App (internal) + Wired + Compressed`,
  приближение к Memory Used в Мониторинге. Отдельно показываются кэш
  (`external + purgeable`), свободная память и Used в стиле `top`
  (`active + inactive + speculative + wired + compressed`).
- **Процессы**: `proc_pid_rusage(RUSAGE_INFO_V2)` → `ri_phys_footprint`,
  как в колонке Memory Мониторинга/`top`, а не RSS. Опрос раз в 5 секунд.

Отнесение ключей к CPU/GPU определено нагрузочными тестами
(`probe/senscan.c` + `probe/gpuburn.swift`): под CPU-нагрузкой `Tp*` +28 °C,
под GPU — `Tg*` +39 °C.

## Безопасность

1. **По умолчанию — auto.** Пока `fanctld` не запущен, управляет SMC
   (состояние фабричное, вентиляторы могут останавливаться в покое).
2. **Плавность.** Цель меняется не более чем на `--slew` (300 RPM) за тик
   (500 мс) — без рывков и шока для подшипника.
3. **Аварийный подъём.** При `maxTemp ≥ critical` (по умолчанию 95 °C) оба
   вентилятора принудительно идут на максимум (`F{n}Mx`), режим — «авария».
   При `≥ warn` (85 °C) пол поднимается до 60–100 % диапазона.
   Выход из аварии — с гистерезисом 3 °C.
4. **Всегда возврат в auto** по SIGINT/SIGTERM и по команде `quit`.
5. **Восстановление после падения.** При старте `fanctld` обнаруживает
   `F{n}Md = 1` и возвращает управление SMC. Установленный LaunchDaemon
   автоматически перезапускается после `kill -9`/crash; после штатного `quit`
   демон остаётся остановленным.
6. **Fail-safe при ошибках.** Потеря всех температур или чтения вентиляторов
   в течение трёх циклов включает emergency. Ошибки записи повторяются,
   попадают в статус/лог и также включают защитный режим. Если вернуть auto
   при завершении не удалось, демон завершается с ошибкой и LaunchDaemon
   повторяет запуск.
7. **Запись только от root.** Сокет `/var/run/fanctl.sock` (0660, root:admin)
   позволяет администратору задавать цель, но не даёт писать в SMC напрямую.
   Клиенты обрабатываются неблокирующе и отключаются после 2 секунд без данных.

> Рекомендация: во время длинного инференса запускайте демон заранее
> (`fanctl start`) и держите ползунок с запасом — например, 3500–4500 RPM
> для M1 Max, или оставьте auto и следите за графиком.

## Отладка

Каталог `probe/` — утилиты, которыми исследовалась машина:

```bash
cd probe
clang -DSTRUCT_PAD=0 smc_probe.c -o probe_nopad -framework IOKit && ./probe_nopad  # все ключи SMC
clang smc_wtest2.c -o smc_wtest2 -framework IOKit && sudo ./smc_wtest2             # тест записи (всегда возвращает auto)
clang hidtemp.c -o hidtemp -framework IOKit -framework CoreFoundation && ./hidtemp # HID-датчики
clang senscan.c -o senscan -framework IOKit && ./senscan 15                       # корреляция при нагрузке
```

Лог демона: `/tmp/fanctld.log` (при `--log` — ещё и CSV).

## Ограничения

- Запись в SMC требует root; GUI не может запустить демон без пароля администратора.
- При запуске вручную без LaunchDaemon `kill -9` оставляет последний
  принудительный режим до следующего запуска `fanctld`.
- Аварийное управление использует SMC-температуры. HID/PMU предназначены для
  мониторинга; отдельных аварийных порогов SSD и батареи пока нет.
- Некоторые защищённые системные процессы могут быть пропущены, если macOS
  не разрешает прочитать их `ri_phys_footprint` без дополнительных прав.
- Привязка SMC-ключей проверена на M1 Max; для других моделей нужна своя
  проверка датчиков и пределов вентиляторов.
- Пороги/шаг задаются аргументами `fanctld` (или командой `thresholds` в сокете).
